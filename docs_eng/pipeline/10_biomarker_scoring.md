# 10. Biomarker Scoring

**Document Version:** 1.0.0  
**Last Updated:** 2026-05-06  
**Korean Sync:** `docs/pipeline/10_biomarker_scoring.md` is the same-version Korean source.

Pipeline step ⑩. Integrates ⑧ feature extraction and ⑨ biomechanical proxy
output into interpretable digital biomarkers and a per-rep composite movement
quality score.

Two record types are emitted:
1. **`BiomarkerRecord`** — pass-through individual metrics with `source_fields`
   provenance, suitable for table-style reporting.
2. **`BiomarkerScoreRecord`** — per-rep composite score (0–100) with
   per-domain sub-scores, dynamic floor, and per-feature deduction audit.

Corresponds to dissertation §7. Scores are anchored to a synthetic-normal
baseline; they are **not** clinical thresholds and must not be reported as
diagnostic results.

---

## 1. Pipeline Position

```text

→ ⑧ Feature Extraction          (FeatureRecord list)
→ ⑨ Biomech Proxy               (BiomechRecord  list)
→ ⑩ Biomarker Derivation         ← this step
```

Required inputs:
```text
feat_records          list[FeatureRecord]   from ⑧
biomech_records       list[BiomechRecord]   from ⑨
exercise_definition   includes feature_domains, biomechanical_focus, quality_rules
definition_version    exercise YAML version string (provenance)
baseline JSON         data/reference/baseline_zscore.json
                      generated by scripts/compute_baseline.py
```

## 2. Design Principle

```text
Allowed:
    Per-domain sub-scores from Z-score deductions against synthetic-normal baseline
    Composite score with documented domain weights
    Dynamic floor proportional to mandatory-ROM achievement
    Per-feature deduction audit list with z, weight, deduction
    Pass-through provenance from FeatureRecord / BiomechRecord

Not allowed:
    Clinical thresholds for "normal" vs "abnormal"
    Patient classification labels
    Hard-coded mean / std (must come from baseline file)
    Disease-prediction outputs
    Single-number summary without per-domain transparency
```

## 3. Two-Stage Output

### 3-1. BiomarkerRecord (pass-through)

Each FeatureRecord and BiomechRecord becomes one BiomarkerRecord with the
same value, unit, and provenance. No transformation other than wrapping with
the YAML version (`definition_version`).

```python
@dataclass
class BiomarkerRecord:
    biomarker_id:       str
    exercise_id:        str
    definition_version: str
    source_fields:      list[str]   # required; raises ValueError if empty
    rep_id:             int | None
    value:              float
    unit:               str         # torso_length_ratio | degree
                                    # | dimensionless_cv | second
    note:               str | None
```

### 3-2. BiomarkerScoreRecord (composite)

Per-rep movement quality summary, computed against the synthetic-normal
baseline. One record per `rep_id`; sequence-level fallback when no reps are
annotated.

```python
@dataclass
class BiomarkerScoreRecord:
    score_id:           str               # always 'rep_quality_score'
    exercise_id:        str
    definition_version: str
    rep_id:             int | None
    domain_scores:      dict[str, float]  # 0–100 per domain
    floor_applied:      dict[str, bool]
    deductions:         list[dict]        # per-feature audit
    final_score:        float             # weighted composite
    source_fields:      list[str]
```

## 4. Domain Weights

Hard-coded in `scoring.DOMAIN_WEIGHTS`:

```text
spatial   40 %     form completeness (ROM, symmetry, shape)
temporal  30 %     pacing and consistency
control   20 %     stability and compensation
                   (intentionally low so adherence is not over-penalized)
biomech   10 %     relative load-distribution tendency
```

Composite formula:

```text
final_score = Σ_d  W_d · domain_score_d
```

Domain assignment is by `feature_id` / `metric_id` prefix:

```text
spatial.*    → spatial      temporal.*   → temporal
control.*    → control      biomech.*    → biomech
other        → ignored
```

## 5. Z-Score Deduction Formula

For each feature `i` in domain `d`:

```text
σ_eff_i  = max( σ_baseline_i,  STD_FLOOR_RATIO · |μ_baseline_i|,  STD_ABS_FLOOR )
           STD_FLOOR_RATIO = 0.10
           STD_ABS_FLOOR   = 0.01

Z_i      = ( value_i − μ_i ) / σ_eff_i
w_i      = 1 / n_features_in_domain          (equal within-domain weighting)
deduct_i = w_i · | Z_i |

raw_score_d   = max( 0, 100 − Σ_i deduct_i )
domain_d      = max( floor_dynamic, raw_score_d )
```

The σ floor prevents near-zero σ from blowing up the Z-score on features
that are essentially zero in the synthetic-normal baseline (e.g. lateral
pelvic shift in a clean squat). A 1 % torso-length deviation thus yields
`Z ≈ 1` rather than `Z → ∞`.

## 6. Dynamic Floor (Mandatory-ROM Anchored)

```text
mandatory_ROM_ratio = mean(  min( ROM_i / ROM_baseline_i,  1.0 )  )
                      over primary-joint ROM features in the rep

floor_dynamic = 50 · clamp( mandatory_ROM_ratio,  0.0,  1.0 )
```

Rationale: a rep that achieves the required ROM should not be punished into
the floor merely because of compensation movements. The floor preserves a
half-credit for completing the movement, even if many control deductions
apply.

```text
ROM achievement    floor      maximum penalty
────────────       ─────      ─────────────────
 100 %              50 pts    50 pts
  80 %              40 pts    60 pts
  50 %              25 pts    75 pts
   0 %               0 pts   100 pts
```

`floor_applied[domain] = True` records every domain that hit the floor for
that rep, surfacing the rep-by-rep coupling between mobility and control.

## 7. Synthetic-Normal Baseline

```text
File         data/reference/baseline_zscore.json
Generator    scripts/compute_baseline.py  (runs the pipeline on synthetic
                                           normal data and aggregates μ, σ)

Schema       { exercise_id: {
                 feature_id: { "mean": float, "std": float },
                 ...
               }, ... }
```

Loaded by `load_baseline()`; missing file → `BiomarkerScoreRecord`
computation is **skipped with a `UserWarning`** rather than raising, so
that ⑧ + ⑨ pass-through records are still returned.

The baseline is a synthetic engineering reference, not a population norm.
Do **not** report Z-scores against this baseline as patient classifications.

## 8. Deduction Audit

Every BiomarkerScoreRecord carries a per-feature audit list:

```python
deductions = [
    {
        "domain":         "spatial",
        "feature_id":     "spatial.rom.left_knee",
        "value":          85.4,
        "baseline_mean":  92.1,
        "baseline_std":   3.5,
        "z":              -1.91,
        "w":              0.143,
        "deduction":      0.273,
    },
    ...
]
```

The list is consumed directly by `plot_attribution_heatmap()` in ⑪
visualization to surface "why this rep lost points" at the individual
feature level.

## 9. Entry Point

```python
from movement.biomarker import derive_biomarkers

biomarker_records, score_records = derive_biomarkers(
    feat_records,
    biomech_records,
    exercise_definition,
    definition_version=exercise_definition.version,
    baseline_path=None,    # default: data/reference/baseline_zscore.json
)
```

Behavior:
```text
- Always returns biomarker_records (pass-through from ⑧/⑨)
- Returns empty score_records list if baseline file is missing
- Iterates over distinct rep_ids in the input records
- Falls back to a single sequence-level score if rep_id is unset everywhere
```

## 10. Linkage to Existing Clinical Scales

The composite is engineered to **mirror** the structure of established
functional movement assessments (e.g., FMS-style 0–3 deductions, OAB-style
binary checklists) but is not directly comparable to them. The linkage is
explicit at the audit-list level:

```text
spatial deductions    → "form" sub-criterion        (FMS scoring rubric)
temporal deductions   → "control" sub-criterion     (within FMS / SFMA)
control deductions    → compensation deduction      (FMS movement screens)
biomech deductions    → load-distribution tendency  (no direct FMS equivalent)
```

⑪ visualization is responsible for surfacing the audit list in a clinician-
readable layout; this step only provides the data.

## 11. Provenance

```text
BiomarkerRecord.source_fields         inherited from FeatureRecord / BiomechRecord
BiomarkerScoreRecord.source_fields    ['feature_domains', 'biomechanical_focus',
                                        'quality_rules']
```

`derive_biomarkers()` enforces provenance at construction time:
records whose source FeatureRecord / BiomechRecord had an empty
`source_fields` are silently dropped from the BiomarkerRecord list (the
underlying records would have raised `ValueError` already).
